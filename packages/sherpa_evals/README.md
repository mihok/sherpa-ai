# sherpa_evals

Sherpa's evaluation harness (the L0–L4 plan of
[R11 §9.9](../../docs/research/11-agent-context-safety.md)) and its host
performance benchmarks with CI budgets
([R12 §3.7–3.8](../../docs/research/12-mobile-ux-ci.md)).

Every suite drives the real code: `AgentRunner`, `LadderContextManager`
and its strategies, `HandoffBuilder`, the provider stream parsers,
`LlamaCppProvider` on the host engine, and in-process `DartMcpServer`s
behind the real MCP client stack (`McpServerManager`, `ToolHygiene`,
`McpToolRouter`). Nothing is faked above the transport except the model,
when `--model scripted`.

```sh
export PATH=/opt/flutter-sdk/flutter/bin:$PATH
cd packages/sherpa_evals
dart run sherpa_evals:eval --suite all --model scripted     # the CI gates
dart run sherpa_evals:bench                                  # host benchmarks
dart run ../../tools/perf_gate.dart --results build/bench --baselines ../../bench/baselines/linux-ci
dart test
```

Reports go to `build/evals/<suite>.json` and `.md` (`<suite>.local.json` for
real models) plus `summary.md`; `build/` is gitignored.

## Suites

| Suite | What | Headline metrics (gated for `scripted`) |
|---|---|---|
| **L0** | Deterministic harness invariants: crash and resume at every durable operation with exactly-once accounting at the servers; the approval-gate matrix (taint × tool class × mode × grant); rug-pull detection through hash pins; constraint carry-forward over rolling compaction | `duplicate_side_effects` = 0, `silent_losses` = 0, `pairing_violations` = 0, `reprompts_after_decision` = 0, `unsafe_auto_runs` = 0, `rugpull_detection_rate` = 100%, `stale_grants_honored` = 0, `constraint_retention` = 100% |
| **L1** | Parser conformance corpus: 160 golden raw outputs per family and parser path (OpenAI chat with server profiles, Responses, Anthropic, on-device engine), well-formed and malformed, each fed whole and in fixed and random SSE chunks | parse, clean-parse, repair, false-repair, wrong-call and block rates; `chunking_instability` = 0; no case that passed in the baseline may fail |
| **L2** | BFCL-style function calling: 50 BFCL v4 cases (20 simple, 10 multiple, 10 parallel, 10 irrelevance) converted to Sherpa `ToolDefinition`s, sent through Sherpa's own provider adapter, scored with a port of BFCL's AST checker | overall / AST / irrelevance accuracy, schema-valid rate, tool-call rate, repairs per 100 calls, TTFT, prefill and decode t/s, peak RSS |
| **L3** | Long-horizon state tasks (MCPMark / τ-bench style): 10 tasks over stateful fake MCP servers (notes, calendar, files, a shopping basket with handles), a scripted user, k trials, a verification function over the final server state | `pass_at_1`, `pass_hat_k` (= 100% scripted), tool-error rate, approval prompts per task (UX cost), deferred-tool share |
| **L4** | Compaction fidelity: 40/60/80-turn scripted sessions with planted constraints, preferences, paths, handles and completed side effects; 0 (control), 1, 2 and 4 forced compactions; then a retention probe, a duplicate-side-effect checklist probe and two handle probes | retention per field, `duplicate_side_effects` = 0 outside documented known issues, task success vs. the uncompacted control, handle lookups, ledger diagnostics, summary token cost (and summarizer tokens for model strategies) |
| L5 | Prompt injection (AgentDojo-style) | **deferred**, see Known gaps |

### L0 — deterministic invariants (`data/l0/`)

* Durability: each scenario of `durability.json` runs once cleanly to
  enumerate its durable operations (store writes, tool calls reaching a
  server), then for every k a process dies before operation k+1 and a fresh
  process resumes on the same store and servers (145 crash points). Servers
  count side effects per idempotency key.
* Approval matrix (`approval_matrix.json`, 416 cells) against the
  R11 §9.6.7/9.7 oracle; the 7 cells where `ApprovalPolicy` deliberately
  differs (built-in tools exempt from taint gating) are known issues.
* Rug pull (`rugpull.json`): changed definitions with and without
  `list_changed` are quarantined before the next segment, and old grants stop
  applying.
* Carry-forward (`carry_forward.json`): constraints and preferences survive
  three rolling extractive compactions; the ledger lists each write once.

### L1 — parser corpus (`data/l1/corpus.json`, generated by `tool/gen_l1_corpus.dart`)

Case policy `baseline`: the corpus documents current gaps, so a case may
fail only if it failed in `baselines/L1.scripted.json` (6 do today: name
corrections, below).
L1 scores the parser layer only; name corrections (typos, wrong case, a
dropped namespace) may still be recovered later by `McpToolRouter` name
resolution, which L1 does not exercise.

### L2 — BFCL-style (`data/l2/bfcl_subset.json`)

`tool/convert_bfcl.dart` takes every Nth entry of BFCL v4
`simple_python`, `multiple`, `parallel` and `irrelevance` (Apache 2.0, see
`data/l2/LICENSE.bfcl`): Python types become JSON Schema and dots in
function names become underscores, as BFCL does for OpenAI-style function
calling. With `--model scripted` an oracle answers with the ground truth,
which proves the conversion and the scorer (100% expected), not a model.

### L3 — state tasks (`lib/src/suites/l3_tasks.dart`)

Each task: initial state, the scripted user's messages, a recorded ideal
trajectory, and `verify(world, before)` comparing the final state with the
goal (including "nothing else changed": no second note, no extra order).
The ideal trajectory is a policy over the request the harness actually
built: it reads handles (`note_id`, `basket_id`, `line_id`) from the tool
results the model was shown and goes through `call_tool` when the router
deferred the tool, so a lost or truncated handle fails it like a real model.
Scripted runs use two tool budgets (`local`: 8 tools; `tiny`, ≤ 2B: 5 tools,
so multi-server tasks run deferred), k = 4. Real models sample at
temperature 0.7, top-p 0.8, top-k 20 with seed 1000 + trial (pass^k needs
variance), k = 2 by default. The scripted user sends its follow-ups in
order, and answers one leftover question with "Yes, please go ahead."

### L4 — compaction fidelity (`data/l4/sessions.json`, `known_issues.json`)

Each session turn is a user message the scripted model answers with the
planned call (create a note or event, write or append a file, read a
document) and a short reply. Compaction is forced with
`LadderContextManager.compactNow` (the "Compact now" path) before evenly
spread turns, and the overlay persisted, so later turns run on the
summarized view. Then:

* retention: each planted item must be visible in the model-visible context
  of the next request (summary + kept tail);
* checklist probe: the user lists every completed action; the scripted model
  redoes each one it cannot see as done (its call and result in the kept
  tail, or a summary line "… → done" with an identifying value: title, path,
  appended text, or the first 40 characters of a body or content); the
  servers count re-applied calls. `retention_side_effects_strict` also
  requires the line to name the tool and its key argument;
* handle probes: update the oldest note and move the oldest event; without
  an id attributed to that title in context the model searches first
  (`handle_lookups`).

Variants: `deferred` (on-device budget, every call through `call_tool`)
and `directApp` (remote budget, direct calls), both wired as
`app/lib/bootstrap.dart` (`toolLookup` plus `ApprovalPolicy.annotationsFor`);
`deferredLookupOnly` and `directLookupOnly` wire `toolLookup` only, so every
MCP hint is untrusted and declared reads stay in the side-effect ledger (a
stress test of its cap). With `--model local:…` the summarizer is
`ModelContextStrategy` on that model (variant `deferred`).

The ledger diagnostics (`ledger_*`) read the final summary: read-only calls
in it, lines that do not name the tool that ran, calls folded into per-tool
aggregate lines (`ledger_folded_calls`), and completed actions in neither
the ledger nor the kept tail (`ledger_evicted_effects`).

## Running

| | |
|---|---|
| scripted (CI) | `dart run sherpa_evals:eval --suite all --model scripted` |
| one suite / cases | `--suite L3 --only shop,cross` (ids containing any entry), `--limit 5`, `--trials 4`; add `--no-gate` for subsets (their metrics differ from the full baselines) |
| local model (host) | `SHERPA_ENGINE_LIB=/opt/vendor-src/sherpa-engine-build/host-shared/libsherpa_engine.so dart run sherpa_evals:eval --suite L2,L3 --model local:/opt/models/Qwen3-0.6B-Q4_K_M.gguf` (`--context 4096`, `--threads 2`; the CPU is shared, keep subsets small) |
| remote model | `--model remote:provider.json` or inline JSON: a `ProviderConfig` plus `model` and `apiKeyEnv`, e.g. `'{"id":"openai","kind":"openaiCompatible","baseUrl":"https://api.openai.com/v1","model":"gpt-5-mini","apiKeyEnv":"OPENAI_API_KEY"}'` |
| report only | `--no-gate` (exit 0 even when a gate fails) |

`--model local:…` loads the engine through
`package:sherpa_inference/engine.dart`, the package's Flutter-free entry
library (FFI host, `LlamaCppProvider`, lifecycle, types), so `dart run` works
without Flutter.

L0 and L1 always replay the harness and the corpus (the model argument does
not change them). Real-model runs use case policy `none`: they report, they
do not gate.

### L2 on a device

The host number is a smoke test on a shared CPU; R11 wants L2 per model and
quantization on reference phones. `runBfcl(cases, provider:, modelId:, …)`
in `lib/src/suites/l2_bfcl.dart` takes the cases as data and does no file
access, so a device harness can call it with the app's own provider:

1. Copy `data/l2/bfcl_subset.json` into the device test as a string
   constant (or an asset) and decode it.
2. In an `app/integration_test` test (`flutter test integration_test/<x> -d
   <device>`), build the provider the app uses on that platform
   (`LlamaCppProvider` over the Android process host or the iOS FFI host)
   with the GGUF under test, call `runBfcl`, and print
   `jsonEncode(report.toJson())`; collect it from the device log.
3. Add `--profile` to keep timings honest; TTFT and t/s then come from the
   engine's `PerfSample`, peak RSS from the host process, and thermal state
   needs the platform tools (R12 §3.9).

This is not wired into `app/` (another team owns it) and has not been run
on hardware.

## Gate semantics

### Evals (`lib/src/gate.dart`)

1. Every metric with an absolute bound (`min`, `max`) must meet it.
2. Cases, per suite policy: `all`: every case passes; `baseline`: no case
   that passed in the baseline fails (L1); `none`: report only (real
   models). A case with a `knownIssue` never fails the gate; one that passes
   anyway is a warning, so the entry gets removed.
3. Against `baselines/<suite>.<kind>.json`: no directional metric regresses
   (`higher`, `lower`, `equal` for exact invariants) beyond its tolerance
   (default 0; baselines keep 6 decimals and are compared at that
   precision). New metrics and cases are warnings.

Rebaseline after an intended change:
`dart run sherpa_evals:eval --suite all --model scripted --update-baseline`,
then review the diff of `baselines/*.scripted.json` (tolerances are kept).

### Performance (`tools/perf_gate.dart`, R12 §3.8)

Baselines live in `bench/baselines/<device-class>/<scenario>.json`:

```json
{"scenario": "markdown_stream", "device_class": "linux-ci", "min_samples": 5,
 "metrics": {"p90_us_per_token": {"baseline": 106.4, "max_regression_pct": 150, "abs_max": 1064.3},
             "tokens_per_s": {"baseline": 23852.4, "better": "higher", "max_regression_pct": 60, "abs_min": 2385.2}}}
```

* Each result metric is the **median of N runs** (`bench` writes every run;
  the gate recomputes the median).
* Lower-is-better (default) fails when the median exceeds
  `min(abs_max, baseline + max(baseline × max_regression_pct / 100, min_abs_tolerance))`;
  higher-is-better fails below `max(abs_min, baseline − max(baseline × pct / 100, min_abs_tolerance))`.
  `min_abs_tolerance` (optional) is an absolute floor on the allowed change,
  for counts whose baseline can be 0 (missed frames, GCs): without it a 0
  baseline would tolerate nothing.
* A run with fewer than `min_samples` samples is **invalid** (fails); so is
  a frame-timing run with `frame_count < min_frames`.
* A missing or skipped result fails unless the baseline is `optional`
  (the engine scenario: no engine or model on CI runners).
* `linux-ci` baselines were measured here (4 shared vCPUs). Runners differ,
  so margins are generous: latency may grow 150% (p99 200%), throughput may
  drop 60%, caps at 10×; the deterministic bundle size may grow 25%.

Rebaseline: add the **`perf-rebaseline`** label to the PR and re-run the
`perf` job (adding a label does not start a run). The gate then only
reports, and `tools/perf_gate.dart --rebaseline` writes new baselines
(keeping each metric's margins) into the `perf-baselines` artifact; review
them, copy them to `bench/baselines/linux-ci/` and commit. Locally:
`dart run tools/perf_gate.dart --rebaseline --results build/bench --baselines bench/baselines/linux-ci`.

## Findings: harness weaknesses the suites revealed

Findings 1–4 are fixed; each fix is gated by the suite that found it.

1. **Completed side effects were lost from the summary after repeated
   compaction, and a faithful agent redid them (L4; fixed).** The summary's
   side-effect ledger (`CompactionSummary.maxLedger` = 40, newest kept) filled
   with read-only calls and evicted the oldest completed writes: 9 cases, 42
   duplicated actions, 30 of them state-changing. Causes: the app wiring
   judged MCP tools by their untrusted defaults (`app/lib/bootstrap.dart` now
   passes `annotationsFor`), and deferred calls were ledgered as the
   `call_tool` proxy (declared destructive, so every proxied read counted),
   rendered as `call_tool {"arguments":{...},"name":...}` cut at 120
   characters, with taint and handles attributed to the proxy.
   Fix (sherpa_core `summary_harvest.dart`, `compaction.dart`): a proxied
   result is resolved to the tool that ran (`ToolResultPart.metaTool` /
   `metaServerId`) before the read-only check, the ledger entry, taint and
   handles; the preview puts the key argument first (path, then
   title/name, then ids) and clips long values one by one; calls the loop
   answered without running them are marked `SummaryComposer.metaNotRun`;
   and `CompactionSummary.capLedger` never drops a write: declared reads
   (untrusted read-only hints) are folded per tool, then dropped, and only
   then are the oldest writes folded into one line per tool with their
   count, key arguments and call ids. Now: 0 duplicates in every variant,
   including the lookup-only ones; `known_issues.json` is empty.
   `test/l4_test.dart` "the checklist probe is a real probe" now proves the
   probe with a summarizer that drops the ledger.
2. **State handles lost what they identify after compaction (L4; fixed).**
   The summary listed `note_id = note_x (tool)` without its title, so 45
   handle probes needed a search. `StateHandle.label` keeps the title or name
   next to the object's first id in the result, else the creating call's
   title/name argument, merged across compactions; rendered as
   `note_id = note_x for "Groceries" (notes__create_note)`. Now 0 lookups.
3. **Duplicate JSON keys executed silently (L1; fixed).**
   `{"city":"Paris","city":"Rome"}` ran `get_weather(city: Rome)` on the
   llama.cpp profile and the engine path, not marked `repaired`. Strict mode
   in `ToolArgumentsRepair` (sherpa_providers; also the Anthropic decoder)
   now refuses, as an invalid call whose `argumentsError` names the key:
   duplicate keys (strict and lenient JSON, stringified too), chat-template
   tokens inside the arguments (Gemma 4's leaked `<|"|>` delimiters), and an
   unquoted multi-word value in arguments that also needed a structural
   repair or that runs into the next key (`{"city": Paris Tokyo, "unit":
   celsius]`); `{"city": New York}` alone is still a flagged repair. The
   engine path (`EngineEventMapper`, sherpa_inference) now parses with the
   same `ToolArgumentsRepair` (`package:sherpa_providers/tool_arguments.dart`),
   so it also decodes stringified arguments, treats `null` as `{}` and emits
   `tool_args_repaired`. L1: false repair 15.1% → 0%, 144 → 154/160.
4. **Identical parallel calls both ran (L3, real model; fixed).** Qwen3-0.6B
   emitted two `<tool_call>` blocks with the same `create_note` arguments in
   one turn (distinct call ids); the harness asked twice and created two
   notes. `AgentRunner` now runs only the first of identical calls in one
   reply (same resolved target, same canonical arguments) unless the tool is
   read-only or idempotent per the trust-aware annotations. Once the
   original is decided, each copy gets the result "Duplicate of call <id>,
   not run…" with the original's outcome (an error only if the original
   failed or was declined: told "error", Qwen3 issued the same call a third
   time in the next step), so pairing stays valid with no second approval
   sheet; plus an audit entry and a `tool_call_duplicate` notice, also after
   a resume. L3 task `notes.parallel_duplicate_create` replays the trace.
5. **Fixed in this package while building it:** the eval gate compared
   6-decimal baselines with a 1e-9 epsilon, so an unchanged ratio such as
   99/107 "regressed" against its own baseline.

## Known gaps

* **L5 (prompt injection) is deferred**: no attack payload corpus is
  shipped. Existing coverage: sherpa_core's taint and approval tests
  (`packages/sherpa_core/test/taint_test.dart`, the L0 approval matrix) and
  sherpa_mcp's description scanner, hygiene and approval tests
  (`packages/sherpa_mcp/test/router/injection_scanner_test.dart`,
  `hygiene_test.dart`, `approval_test.dart`).
* **L2 real numbers are device-only**: the host figure is a smoke test on a
  shared CPU with 50 cases; battery and thermal throttling need a device
  (R12 §3.9). BFCL multi-turn categories are not converted yet.
* L3 uses a scripted user only (no remote-model user simulator for τ²-style
  dual control), and k = 2 for real models by default (R11 asks for 4).
* L4 with a model summarizer needs `--context 16384` or more (with forced
  compaction only, the 40-turn session does not fit 4096 tokens; the suite
  skips with a note). Real runs default to `household_40` with 0 and 1
  compactions: one summary costs about 8K tokens of prefill (minutes on a
  phone-class CPU), so real runs skip 2 and 4 compactions (`--only` picks
  other sessions, which need a larger window).
* Frame-timing benchmarks have not run on a device here: the
  `android-mid-adreno650-gles` and `android-emulator-api36-swiftshader`
  baselines are placeholders until the first measured run
  (`bench/app/README.md`).
